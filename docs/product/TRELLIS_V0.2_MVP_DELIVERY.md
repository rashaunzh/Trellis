# Trellis V0.2 MVP 交付、验收与下一阶段计划

> 状态：Checkpoint 5 后交付说明  
> 日期：2026-08-14  
> 范围：不包含浏览器自动化验收；该项由另一条任务负责  
> 基线：`docs/product/TRELLIS_V0.2_PRD.md`、`docs/architecture/TRELLIS_V0.2_ARCHITECTURE.md`、`docs/engineering/TRELLIS_V0.2_IMPLEMENTATION_PLAN.md`

## 1. 当前结论

Trellis V0.2 已完成一条可运行的最小学习闭环：

```text
诊断 → 学习地图 → 首周计划 → 学习活动 → 证据提交 → 证据评估 → 节点成长状态变化 → 调整建议
```

本轮交付的意义不是“课程内容已经完整”，而是证明 Trellis 的核心产品假设可以被工程化表达：**系统能够把可信学习路径编排为可执行活动，并根据证据更新成长状态。**

这已经足够作为 V0.2 MVP 骨架进入下一阶段体验打磨和真实用户试学；但还不能宣称完成 PRD 中所有长期验收项，例如综合任务正式提交、AI 六维评分、用户确认掌握、延迟复测自动调度和完整来源目录。

## 2. 已交付范围

### 2.1 产品结构

前台固定为三个一级功能：

- **学习**：按周推进，展示核心/可选活动，进入活动抽屉完成学习。
- **成长**：同一张成长地图展示路线、相邻分支、节点状态、证据和调整记录。
- **工作台**：展示材料、资源、工具与学习节点的映射，而不是普通链接仓库。

不再使用旧的四个平级页面：继续学习、学习路径、复习评估、资源库。

### 2.2 学习闭环

已实现的真实闭环包括：

1. 目标输入和简短诊断；
2. 推荐路线、相邻分支和首周计划；
3. 用户确认路线和计划；
4. 活动开始、证据提交、证据评估；
5. 证据不足时退回修订；
6. 证据接受后节点从 `growing` 进入 `validated`；
7. 产生可解释的调整建议；
8. 用户确认调整建议；
9. 刷新和服务重启后恢复状态。

### 2.3 工程范围

已完成：

- `db/schema.ts` 新增 learning 域表；
- `drizzle/0004_kind_boomerang.sql` 新增迁移；
- `lib/learning/domain/`：类型、内容包、状态机；
- `lib/learning/agents/`：planner、activityComposer、evidenceEvaluator、adjustmentAdvisor 四类接口与规则实现；
- `lib/learning/application/`：学习闭环服务；
- `lib/learning/persistence/d1.ts`：D1 持久化；
- `app/api/learning/`：面向学习闭环的 API；
- `app/learn`、`app/grow`、`app/workbench`：三功能前台；
- `tests/learning-domain/`：领域、API 闭环与持久化恢复测试。

## 3. 最终产品验收口径

### 3.1 本轮可放行标准

本轮可以放行，如果满足：

1. 三个一级功能存在且没有回到旧四页面结构；
2. 学习页能从诊断进入首周计划；
3. 活动抽屉能完成开始、提交、退回、修订、接受；
4. 节点变色由证据评估触发，而不是由“完成按钮”触发；
5. 成长页能说明用户在树上的位置、证据和调整原因；
6. 工作台资源能映射到节点和活动；
7. D1 持久化通过刷新和重启恢复；
8. 测试、lint、build 通过。

### 3.2 不能在本轮宣称已完成的 PRD 项

以下是下一阶段要做的体验和产品能力，不应在演示或文档中伪装为已完成：

1. 综合情境任务的正式提交流；
2. AI 六维或多维量规评分；
3. 用户对“掌握/未掌握”的正式确认；
4. 延迟复测的自动调度；
5. AI 通识 V1 的完整来源目录和节点量规；
6. 用户导入材料后的可信度审计与缺口分析；
7. 外部工具自动同步；
8. 生产部署迁移和 V0.1 数据迁移。

## 4. 产品复盘

### 4.1 已被验证的判断

1. **三功能结构成立**：学习、成长、工作台比四页面结构更贴近使用习惯，也降低选择成本。
2. **地图和成长树应该合并**：用户真正关心的是“我在这张树上的哪个位置、摘了哪些果实、下一步怎么走”，不需要在两个功能间切换。
3. **活动是核心学习单位**：一次活动必须包含路径位置、目标表现、输入材料、学习行为、证据和下一步规则；否则会退化成 todo。
4. **证据驱动是产品可信感来源**：节点状态不能靠打卡或点击完成更新，必须能追溯到证据和评估依据。
5. **动态调整需要边界**：活动可以高动态，周计划要半稳定，长期路线必须版本化并经用户确认。

### 4.2 当前薄弱点

1. **内容可信边界仍粗**：现阶段内容包是启动数据，能支撑 MVP 骨架，但还不构成完整权威课程库。
2. **活动质量还偏模板化**：规则实现可以跑通流程，但还没有充分体现不同知识类型、能力阶段和用户偏好的差异。
3. **成果与能力画像仍偏轻**：已能追溯证据，但“能力系统/成长树果实”的表达还需要更像产品体验，而不只是状态字段。
4. **工作台的资源映射还只是第一版**：需要继续思考飞书、NotebookLM、GitHub、文档等外部材料如何以摘要卡片降低切换成本。
5. **PRD 验收项大于当前闭环**：当前完成的是 MVP 骨架，不是完整学习产品毕业体验。

### 4.3 保持不变的产品原则

后续开发不得改掉以下原则：

- 核心价值是可信的动态学习编排；
- 用户只设置目标、材料和时间，Trellis 负责提出学习路径和周计划；
- 允许跳学，但必须通过证据验证；
- AI 可以提案、解释、评估和建议，但不能静默改变正式路径和能力状态；
- 工作台不是资源收藏夹，资源必须映射到节点、活动、成果或证据；
- 产品重点是学习，不是 todo、课程平台、打卡工具或聊天机器人首页。

## 5. 下一阶段计划

### P0：补齐 MVP 产品验收缺口

目标：让 V0.2 不只是能跑通闭环，而是能完成一次更完整的“学会一点”的体验。

1. **综合任务正式流**
   - 在首期路线中增加一个综合情境任务；
   - 支持正式提交；
   - 输出多维评分、理由、缺口和下一步。

2. **掌握确认**
   - 证据被接受后，展示“系统判断 + 用户确认/纠正”；
   - 用户确认后才写入更强的掌握判断；
   - 保存确认记录和依据。

3. **延迟复测**
   - 为已验证节点生成复测候选；
   - 不做日历提醒，先在成长页或学习页显示“待复核”；
   - 复测结果影响置信度和后续活动。

4. **AI 通识 V1 内容包审计**
   - 明确节点、前置、目标表现和来源；
   - 区分通识、应用开发、产品经理三条方向；
   - 补齐每个关键节点的最低证据标准。

### P1：把体验从“可用”打磨到“想继续用”

目标：增强第一眼可信感和持续学习动力。

1. 优化学习页首屏：一周承诺、当前阶段、为什么现在学；
2. 优化成长地图视觉：当前路线、一层相邻分支、三色状态、已接触标记；
3. 强化成果表达：作品、技能、工具经验、可迁移成果；
4. 强化工作台：用户材料摘要卡、来源可信等级、缺口提示、节点映射；
5. 把活动模板升级为活动编排决策模型，而不是固定文案。

### P2：工程化和生产准备

目标：让系统从个人验证走向稳定生产。

1. 完成浏览器自动化验收并纳入 CI；
2. 明确 D1 远程数据库、迁移、备份和环境变量；
3. 清理旧实现或建立兼容适配层；
4. 审计 V0.1 数据迁移边界；
5. 加入基础可观测性和错误恢复；
6. 明确未来 agent runtime 是否自研、外接或混合。

## 6. 给后续 agent 的执行规则

1. 接手前先读本文件、V0.2 PRD、V0.2 架构和实施计划；
2. 不要重新引入四页面结构；
3. 不要把“活动完成”当成“节点已验证”；
4. 不要把 AI 输出直接写成正式路径或正式掌握状态；
5. 不要为演示写死页面假数据；
6. 不要把浏览器验收结果写成已完成，除非有独立任务提供证据；
7. 每次完成有持久价值的改动，都要更新 `memory/handoff/current.md` 和 `memory/sessions/`。
