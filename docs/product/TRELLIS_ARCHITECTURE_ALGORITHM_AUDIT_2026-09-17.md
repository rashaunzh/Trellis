## 1. 引擎回顾：八环节闭环

产品定义（自 2026-08-12 起稳定）：

> Trellis 面向成人自主学习者，**长期服务所有学习领域**；首期使用 **AI 通识基础** 验证通用内核。

引擎闭环：

```
诉求 → 领域底图 → 诊断 → 个性路径 → 周编排 → 结构化学习 → 掌握评估 → 动态调整
```

关键性质：**引擎是领域无关的，内容包是可替换的。** AI 通识是第一包。判断标准是这个内核能否闭合成"证据驱动的掌握循环"，而不是某个主题学得好不好。

核心主张（决定产品与普通学习工具的分野）：

- **hard_evidence 才能推动 validated，soft_signal 只能影响下一步决策**
- **掌握必须用户确认**（`pending_confirmation` 状态 + `confirm-mastery` 的 confirmed/corrected 双路径）
- **完成 ≠ 通过**："完成"是流程状态，"通过"才满足验收
- **诚实失败**：核心目标未覆盖时输出 `planStatus: limited`，不包装成完整路线

### ① 诉求解析 — 设计不成立

实现 55 行（`goal-analyzer.ts`）：

- 深度：动词表推断（含"做一个/开发/作品"→3，含"了解/入门"→1）
- 领域：`inferDomain` 取**最长的关键词**当领域名
- `targetCapabilityIds: []` 空置

问题：

1. `inferDomain` 取"最长词"没有依据，领域名随分词随机漂移
2. 深度按动词表判定，**规则顺序决定结果**（"我想了解怎么开发"同时命中 DEPTH3/DEPTH1，先查 DEPTH3 判为 3，实际用户表达的是理解层）

用户的一句话目标包含**意图、领域、深度、约束、起点**五类信息，55 行规则无法承担。**这一环必须上模型**（`GoalAnalyzerPort` 接口已预留）。

### ② 领域底图 — 结构对、内容空

`graph.ai.v1`：**38 个节点、6 个概念族**（foundation/use/product/system/model），带前置关系与目标深度（1 解释 / 2 应用 / 3 迁移）。结构正确，不需要更复杂。

两个问题：

1. **`outcomes` 是模板拼接**：

```js
outcomes: [`能解释 ${title} 的关键概念`, `能在真实场景中判断何时需要 ${title}`]
```

38 个节点的"学完能做什么"全是这两句套名字。**领域底图的核心价值恰是"这个节点学完能做什么"，而这正是唯一没写的东西。** 这行代码也直接产出了界面上"能在真实场景中判断何时需要 X；能在真实场景中判断何时需要 Y；……"的重复文案。

2. **存在两套互不相关的领域图**：
   - `lib/ai-literacy-v1.ts`：6 个能力节点，**每个都手写了 `学习结果` / `关键概念` / `情境练习`** —— 质量高，但无课程映射
   - `lib/learning/intelligence/baseline.ts`：38 节点，`outcomes` 是模板，但**挂满 30 门真实课程与章节映射** —— 覆盖广，但无内容

   **一套有内容没课程，一套有课程没内容，两者未打通。** 这是设计层面的重复建设。

### ③ 诊断 — 设计最好的一处，但输入缺失

`LearningSituation` 11 个维度：目标清晰度 / 材料状态 / 水平 / 阶段 / 动力 / 时间压力 / 容量 / 精力 / 行为模式 / 证据质量 / nextBestMove。

这是全库设计水平最高的一处，理由：

- 区分**"没完成任务"的多种原因**（`blocked` / `avoidant` / `restarting` / `input_heavy`）
- 把**"读完"与"会用"分开**（`evidenceQuality`）
- 把**"自报"与"证据"分开**（`soft_signal` 只影响决策）

**致命缺口：这 11 维所需的数据，产品里没有采集点。**

`LearningSituationInput` 需要 `dailyCapacitySignals`（每日可用时间 + 精力）、`behaviorNotes`、`confusionNotes`、`repeatedGaps`、`skippedActivities` 等 21 个字段。而界面上用户能提供的只有"目标 + 每周小时数"，加上事后一个自评按钮。

**结论：诊断器设计的 11 个维度，实际只算出了 2 个，其余走默认值。** 这不是算法错，是**"采集层"缺失**——产品从未设计过这些数据从哪里来。

### ④ 个性路径 — 好算法未启用，启用的输入源坏

存在两套路径算法：

**A. `curriculum-solver.ts`（前台在用）**

流程：目标关键词 → `goalAliases` 正则命中节点 → 前置闭包 → 排序选课（核心节点预算放宽至 5 门，普通 3 门）→ 装配阶段。

设计上修过一个真问题（2026-09-12）：核心节点未覆盖时输出 `planStatus: limited`，不假装完整。**这个设计是对的。**

但根子是坏的：

```js
{ pattern: /产品|product|pm|prd/, nodes: ["pm.problem-framing", "pm.use-case-fit", "pm.capability-design"] }
{ pattern: /评测|评估|eval/,     nodes: ["pm.eval-design", "pm.failure-taxonomy", ...] }
// 命中不了 → graph.nodes.filter(foundation).slice(0, 4)
```

**"个性路径"的个性来自关键词碰撞。** 这就是 2026-09-12 文档记录的"17 条真实模型路线 0 条可用"的机制——不是求解器算错，是喂给它的目标节点集合本身就错。

**B. `adaptive-planner.ts`（未启用）**

包含正确的东西：

- **前置闭包 + 拓扑排序**保证前置在前
- **`satisfied` 概念**：自评达标的节点保留在路线中作上下文，但本周不排基础活动；自评 ≥1 未达标则跳过"建立模型"，直接独立练习
- 按容量填充活动链

**这个设计优于 A，但挂在 `plannerMode: "adaptive_existing_content"` 后面，默认走 `legacy`（即 A）。**

### ⑤ 周编排 — 骨架对、算法粗

`composeWeeklyPlan`：候选节点（前置满足、未跳过、未验证）→ 按 `growing` 优先 + 路线顺序排序 → 6 类活动链按容量填充 → 核心活动承诺 ≤ 容量，可选不计入。

对的部分：区分核心/可选承诺；确定性（同输入同输出，刷新不重排）；区间承诺而非每日课表。

问题：

1. **活动时长写死**（45/45/90/30/30/120），不看节点难度、不看材料实际长度。深度 3 与深度 1 的节点排同样时长
2. **`targetCoreCount = min(8, max(2, floor(capacity / 60)))`** —— 纯按小时数除，不考虑活动间依赖
3. 活动内容不在此层生成，由下游模板拼接

### ⑥ 结构化学习 — 与引擎不匹配

`learning-program.ts` 的原创教学单元质量高（讲解、示例、练习、量规、两组选择题，边界意识清楚）。

但：

- 原先只有 **4 个节点**有对应单元，而领域图有 38 个节点 → 覆盖率约 10.5%（本次 `918141c` 已上架全部 8 个单元，覆盖率仍有限）
- 形态是"讲解 + 闭卷选择题"

**设计断层：`program_check` 产出的是"选择题得分"，而 ⑦ 需要的是"能力信号证据"。两者是两套体系，对不上。** 而且选择题只测记忆，不产生应用层证据。

### ⑦ 掌握评估 — 设计最好，实现最假

**设计（正确）**：

- 每个节点一套**能力信号**（`NODE_SIGNALS`，14 节点 × 5–6 条短语），证据需逐条体现
- 证据状态机：`draft → submitted → accepted / needs_revision`
- 节点状态机：`unstarted → growing → pending_confirmation → validated`
- **`validated` 必须用户确认**（`confirm-mastery`，且支持"纠正"）
- **`soft_signal` 永远不能推动 `validated`**
- 复测失败 → 节点**降级** + 熟练等级减 1

**这套设计是专业的。它回答了"凭什么说你会了"，并且不允许自欺。**

**实现（失效）**：判定为字符串包含，详见第 3 节算法审计 ⑥⑦。核心公式：

```js
accepted = score >= 58 && content.length >= 80 && rubricCoverage >= 0.66
```

其中长度达标即白送约 39 分，**"能力信号覆盖"仅占权重 0.25 —— 意味着系统实际在奖励"写得长、贴了链接"，与引擎的核心主张直接矛盾。**

`reviewEvidence` 中 `const llm = undefined`——模型位留了，注释称"模型增强统一由 Course Intelligence 网关承担"，但那条链不经过此处，因此永远是规则版。

### ⑧ 动态调整 — 全库最实的算法

按优先级分派：前置缺口 > 复测失败 > 重复失败（≥2 次）> 普通退回 > 完成率低 > 有跳过节点 > 正常推进。

亮点：`repeatedSignals()` 计算**"本轮缺失信号 ∩ 上轮缺失信号"**，检测"反复缺失同一能力"。这是**真正的诊断逻辑**，不是模板。

输出结构化（`adjustmentType` / `reason` / `summary` / `actions[]` / `severity`），高严重度需用户确认。

唯一问题：其输入 `missingSignals` 来自 ⑦ 的字符串匹配，因此缺口判断本身可能是错的。

## 3. 算法技术审计（12 个）

| # | 算法 | 类型 | 技术上成立？ | 误差 |
|---|---|---|---|---|
| 1 | 前置闭包 `prerequisiteClosure` | 图 DFS | ✅ 正确 | 零 |
| 2 | 关键词提取 `deriveKeywordsFromText` | 标点切分 | 🔴 **中文失效** | 命中率 ≈ 0 |
| 3 | 节点打分 `scoreNode` | 命中率 | 🔴 **量纲错误** | 必然走 fallback |
| 4 | 选课打分 `courseScore` | 线性加权 + 贪心 | 🟡 权重无依据 | 不可量化 |
| 5 | 材料评估 `scoreMaterial` | 关键词计分 | 🔴 魔法数字 | 不可信 |
| 6 | **信号覆盖 `buildSignalReviews`** | **2-gram 包含** | 🔴 **假阳性 + 假阴性双高** | **基本无效** |
| 7 | **总分合成 `weightedScore`** | 加权求和 | 🔴 **长度主导** | **通过线可凑** |
| 8 | 材料裁决 `verdictFrom` | 阈值分级 | 🟡 输入不可信 | 不可信 |
| 9 | 决策策略 `learning-decision-policy` | 规则引擎 | 🟢 设计好，阈值未标定 | 中 |
| 10 | **调整建议 `adjustment-advisor`** | **优先级树 + 集合交** | 🟢 **最好** | 低（依赖 ⑥） |
| 11 | 状态机 `state-machine` | FSM | ✅ 正确 | 零 |
| 12 | 周容量编排 | 贪心装箱 | 🟡 平均分摊 | 中 |

### 逐项要点

**✅ #1 前置闭包**：标准可达性 DFS，含环保护。38 节点规模下复杂度无问题。
⚠️ 但只保证"前置被包含"，**不保证顺序**。真正的拓扑序只在未启用的 `adaptive-planner.orderCapabilities` 里。

**🔴 #2 关键词提取**：中文没有词边界，按标点切出的"词"实为短语/小句。"我想从零开始学习 AI 产品经理"整句成为一个 token，再拿去 `corpus.includes(keyword)` 匹配节点文本，**永远匹配不上**。这就是"零材料启动"退化为 `slice(0, 4)` 的原因——不是策略问题，是**算法在中文上不工作**。

**🔴 #3 节点打分**：

```js
scoreNode = 命中关键词数 / 关键词总数
```

分母是关键词总数而非节点数，**没有绝对意义**。目标含 10 个词时任何节点最多命中 2–3 个，**永远达不到阈值 0.5 → 正常输入必然走 fallback**。阈值与分母量纲不匹配。

**🟡 #4 选课打分**：线性加权 + 贪心本身成立，但

- 权重无依据（`pinned=20` vs `relation core=4` vs `confidence*4`），行为对权重极度敏感且不可解释
- `mapping.confidence` 既当硬门限（`>= 0.8`）又当加权项（`* 4`），同一量用了两次
- 含硬编码 NLP 补丁：`goal.replace(/(?:没有|无|不具备)\s*(?:编程|python|代码)\s*基础/g, "零基础")`——这类补丁说明底层缺的是语义理解

**🔴 #5 材料评估**：10 个维度全为"关键词命中 → 加固定分"，属二值跳跃（出现"练习"就 +45，不出现 +0，中间无过渡）。常数 `35/18/25/45/70/20/60/30` 无任何来源，未做标定、回归或专家打分集。示例反例：`freshness = 55 + (含"2025/2026/最新" ? 25 : 0)`——**2024 年的材料只要正文出现过"最新"二字，就会得分更高。**

**🔴 #6 信号覆盖（最关键）**：

```js
tokens = signalTokens(label)   // 中文按 2 字滑窗切分
status = directHit || hitCount >= ceil(tokens.length * 0.5) ? "covered" : ...
```

三个错误：

1. **2-gram 假阳性高**："问题陈述拆解" → {`问题陈述拆解`,`问题`,`陈述`,`拆解`}。用户写"我有个**问题**，这个**陈述**不太清楚"即命中 2/4 = 50% → 判为"已覆盖"。**用户完全没做拆解。**
2. **字面子串，非语义**：写"成功标准"命中，写"怎样算做成了"漏掉——**同义表达召回率为 0。**
3. **切词窗口有偏移错误**：`i += 2` 对奇数长词与含非中文字符的词（如"AI 与普通程序区分"）失效（`/^[\u4e00-\u9fa5]+$/` 判定失败），只保留整词，召回进一步下降。

**该算法同时假阳性极高与假阴性极高——不是有偏差，是基本无效。**

**🔴 #7 总分合成**：权重和为 1，加法本身正确。但

```js
parseability   = length >= 80 ? 90 : ...              // 权重 0.15
criteriaCompleteness = length>=80 ? max(_, 65) : _    // 权重 0.15
contentQuality = max(70, min(100, length / 1.5))      // 权重 0.12
credibility    = 有链接且长度够 ? 80 : 65              // 权重 0.10
```

**长度 + 链接即白送约 39 分**，而通过线是 58 分。**"能力信号覆盖"只占 0.25 权重——写够字数、贴个链接、信号覆盖六成，即可通过。** `suggestedLevel` 又与此分挂钩（`score>=85` 给 3 级），因此**熟练等级由长度和词表决定**。

**🟢 #9 决策策略**：多因子分类 → 查表选 nextBestMove，属专家系统，技术成立。因子设计有依据（自我调节学习、掌握学习、间隔复习、支架教学、刻意练习、福格模型）。问题：所有阈值（0.25 / 0.55 / 60 / 150 / 420 / 8 字）未标定；且**无优先级冲突解决机制**——多因子同时成立时由代码顺序而非重要性决定。

**🟢 #10 调整建议**：全库最好的算法。优先级决策树 + 集合交集，优先级有依据，`repeatedSignals` 是真诊断逻辑。

**🟡 #12 周容量**：`floor(capacity/60)` 假设每活动 1 小时，而活动链均值恰为 60，估算在均值上碰巧成立，但不看节点难度。

## 4. "看不出实现了什么"的技术机制

三个被验证的事实：

**事实一：Mastra 完整实现，界面零入口。**

`lib/learning/agents/mastra-workflow.ts` 有一条**十步工作流**，步骤顺序即引擎：

```
assessSituation → auditMaterials → mapCapabilities → planStagePath
→ simulateDynamicAdjustment → createArtifactTask → reviewArtifactEvidence
→ waitForMasteryConfirmation → proposeNextStage → summarizeQuality
```

用 `.then()` 串联并 `.commit()`，`trellisMastraRuntime = new Mastra({...})` 已挂载。

但：前端对 `mastra-runtime` **只调 GET**（拿注册状态，纯展示）；`POST` 返回 **410**（"固定作品工作流演示已退出正式调用链"）；`app/` 内搜 "mastra" 只有该 API 文件，四个页面从未提及。

**结论：一条十步引擎注册完备、可运行，但没有任何用户能触达。它是展品。**

**事实二：外部 agent 未接。**

`CourseIntelligenceModelGateway` 实现认真：主备双 provider、结构化输出（json_schema / json_object / prompt_json）、grounding 校验、失败分类、attempt 记录、缓存、成本记录、trace。

但这是"调用外部模型"，不是"接入外部 agent"。全库检索 MCP——只出现在**课程目录数据**里，**无任何 MCP 协议实现或 agent 互操作层**。且该网关仅被课程智能链使用，由 `TRELLIS_AI_PRIMARY_*` 环境变量驱动；本地未配置时 `builtInModelConfig` 返回 `null`，全部走 `baseline`。**实测全流程未发出任何模型请求。**

**事实三：52 个后端路由，前端只调 29 个。**

后端存在、前端从不调用：`situation/diagnose`（**处境诊断**）、`assessments/submit`、`artifacts/review`、`packages/generate`、`workflows/[id]`、`api-config`。

而 `memory` / `quality` / `eval` / `artifact` 等虽被调用，但仅作 GET 展示，不构成可操作能力。

**因此"看不出实现了什么"是准确的技术描述：引擎每个环节都有代码，但接界面时大部分环节没有入口，有入口的只是只读展示。断的不是引擎，是引擎与用户之间的那一层。**

## 6. 修复优先级建议

### 三个根因（按修复顺序）

**根因一：采集层缺失（设计缺口，此前从未设计过）**

引擎设计为"根据处境与证据决定下一步"，但**处境数据的采集和证据的采集从未被设计**。当前唯一数据来源是：一个目标文本框、一个每周小时数四选一、事后一个自评按钮。

需要补：诊断 11 维的最小采集点、能力信号证据的采集形态。

**根因二：需要语义理解的五环被降级为字符串匹配（实现缺口）**

八环中需语义理解的有五环（①④⑥⑦⑧），其中①④⑦为字符串匹配，⑥为预设答案，仅⑧是真逻辑。

代码中**处处预留了模型位**（`Port` 接口、`evaluateEvidence(input, llm)` 的 llm 参数、版本化 Zod 契约、主备网关），**但无一处真的接上**。

**根因三：两套领域图与两套体系并存（整合缺口）**

- `ai-literacy-v1.ts`（有内容，无课程）与 `baseline.ts`（有课程，无内容）
- V0.2 学习应用（`learning-service` / `agents` / `domain`）与 V0.3 课程智能（`course-intelligence` / `solver`）在前台缝合

### 建议的修复顺序

1. **补采集层设计**（设计工作，先于编码）
2. **接通需语义理解的五环**，优先 ⑦ 掌握评估与 ① 诉求解析——**它们是引擎的头与尾，头错则路线错，尾错则"学会了"为假**
3. **整合两套领域图**
4. **重新设计"确定性校验"层**——接入模型后，校验对象从"字符串"变为"模型输出的引用是否真的来自用户原文"（防编造）。这一层此前未设计
5. **把 Mastra 十步工作流从"展品"改为"主干"**（它已经完整串联了引擎）
6. **接通断掉的四环界面入口**：诊断、结构化学习、掌握评估、动态调整

### 关于 🟡 类算法（4 个参数未标定）的两条路径

- **(a) 标定**：需真实标注数据（如 30 份证据 + 人工判定），再调权重。这是"做一个真评估系统"的成本
- **(b) 不标定，直接上模型**：这些维度（"内容质量""可信度"）本身主观，且参数无依据，不如让模型按量规判断，规则版仅作降级

**建议 (b)**，理由：(a) 所需数据尚不存在，(b) 与根因二一致。

## 7. 需要澄清的技术风险

1. **"形似算法"比"没有算法"更危险。** `scoreMaterial` 有 10 个维度、`weightedScore` 有权重表和归一化、`buildSignalReviews` 有 2-gram 切词——**形式专业，实质是关键词计分卡**。这容易让人误以为评估有效。

2. **接入模型后必须补"引用校验"。** 现有"确定性校验"校验的是字符串包含。改为模型判断后，必须校验：反馈中引用的用户原话是否真实存在于提交内容中、引用的来源是否来自当前材料版本。**这是防"编造用户没说过的话"的最后一道闸门，目前不存在。**

3. **`confidence` 语义污染。** 代码中 `confidence` 至少有两种含义被混用：映射可信度（`mapping.confidence`）与评估置信度（`assessment.confidence`），且 `assessment.confidence` 是 `score/100` 的直接换算，**不是校准过的概率**。运行时切勿把模型自报的 confidence 当作准确率。

## 8. 审计结论

- **架构骨架合理，不需要推倒。** 八环节闭环、Port 可替换接口、状态机、证据分层、人确认掌握、诚实失败——这套设计是专业水准。未发现结构性设计错误
- **12 个算法中：✅ 完全正确 2 个（前置闭包、状态机）；🟢 设计可用 2 个（决策策略、调整建议，是真正的资产）；🟡 结构对但参数未标定 4 个；🔴 技术上不成立 4 个（关键词提取、节点打分、信号覆盖、总分合成）**
- **决定性事实：④⑦两环（诉求→路径、掌握评估）落在 🔴 区，而它们是引擎的头与尾。** 头坏则路线是错的，尾坏则"学会了"是假的。两处损坏原因相同——**用字符串匹配承担了本该由语义理解承担的任务**
- **"看不出实现了什么"的机制是：引擎完整，但引擎与用户之间缺少那一层。** 大部分环节没有界面入口，有入口的只是只读展示；Mastra 十步工作流已完整串联引擎，却被定位为"演示"（POST 返回 410）
- **下一步不该是加功能，而是三条：补采集层设计 → 接通语义环节（先⑦后①）→ 整合两套体系**
