# Trellis MVP 产品需求文档（提案）

> 状态：待确认  
> 日期：2026-08-13  
> 本文用于替代“先堆功能页、再解释产品”的实现方式。确认前不作为编码授权。

## 1. 一句话定义

Trellis 是一个以真实学习证据为依据、持续决定“下一步最值得学什么”的个人学习系统。

它不销售一套固定课程，也不要求学习者自己设计课程。学习者只需要说明想解决的问题、现实约束和已有材料；Trellis 负责建立学习路径、组织下一步、检查证据并提出调整。

## 2. MVP 要验证的问题

MVP 不试图证明 Trellis 已经是一所完整的 AI 学校。它只验证一个核心闭环是否有价值：

```text
我想获得一种能力
→ Trellis 判断当前缺口
→ 给出一个能立即开始的学习动作
→ 我完成动作并留下证据
→ Trellis 根据证据决定继续、补强还是复习
```

如果系统只能生成漂亮路线图，不能根据证据改变下一步，MVP 失败。

如果系统只是把文章、题目和进度条放进页面，不能解释为什么现在做这件事，MVP 失败。

## 3. 首期范围

### 3.1 验证领域

- 首期领域：AI 通识。
- AI 产品方案可以作为综合应用情境，但不是用户分类，也不是 Trellis 的职业定位。
- 数学、Python、机器学习和深度学习只在目标确实需要时成为分支，不默认出现在所有人的路径中。
- 学习者不负责设计六项能力、题目顺序、课程目录和评分量规；这些属于 Trellis 的内容设计责任。

### 3.2 用户毕业结果

学习者能够：

1. 解释现代生成式 AI 的基本工作方式、概率性和失败边界。
2. 判断一个问题是否适合使用 AI，并明确人机责任。
3. 组织上下文、来源和工具完成可复核任务。
4. 在直接生成、检索、工具调用和 Agent 之间做基础选择。
5. 为 AI 功能设计测试、失败检查、拒答和人工确认。
6. 识别隐私、安全、权限、偏见、版权和成本约束。
7. 将以上判断组织成一份可评审的 AI 功能方案。

“独立编码”“训练模型”和“掌握完整数学体系”不是统一毕业要求。是否加入这些目标，由学习诉求决定，而不是由系统预设。

### 3.3 体量原则

- 12–18 小时、24–36 星是内容团队用于控制首期路径的设计区间，不是首页卖点，也不是对所有人的硬承诺。
- `0.5 星 = 15 分钟`，星只表示粗粒度投入估计。
- 学习按周容量编排，不绑定每天，不建设打卡、连续天数和实时计时器。
- 熟练等级采用无证据、理解、应用、迁移四级；它与“待学习、学习中、待验证、需复习”等学习状态分开。

## 4. 用户是谁

MVP 不按年龄、职业或学历预设人格类型。路径差异来自：

- 想解决的问题；
- 希望达到的深度；
- 已有知识和作品证据；
- 已选材料及其覆盖范围；
- 每周可投入容量；
- 在学习活动中的真实表现。

首次只服务产品所有者这一名单用户，但所有运行数据保留 `ownerId`，避免未来改造成多用户时推翻数据边界。

## 5. 核心使用场景

### 场景 A：第一次进入

用户用自然语言说明“想学什么、为什么现在学、希望能做成什么”。Trellis 最多进行少量必要追问，然后完成短诊断和材料检查。

系统返回的不是人格标签或考试成绩，而是：

- 对目标的复述；
- 当前已有证据与未知项；
- 建议学习范围；
- 为什么从这里开始；
- 第一周预计投入；
- 需要用户确认的重大假设。

### 场景 B：回来继续学习

用户打开 Trellis 后，首先看到唯一明确的下一步，而不是功能菜单、课程目录或数据仪表盘。

下一步必须说明：

- 为什么现在做；
- 它属于哪项能力；
- 预计投入；
- 具体动作；
- 完成后留下什么证据；
- 完成后可能发生什么变化。

用户可以直接开始、查看路径依据、调整本周容量，或向导师提问。

### 场景 C：完成一次学习动作

学习动作可以发生在 Trellis 内，也可以指向外部材料或工具。Trellis 只承载必要的引导、练习、反馈和证据回收，不复制完整外部课程。

完成后系统收集最小证据，例如：

- 一段解释；
- 一个情境判断；
- 一份小方案；
- 外部作品链接；
- 一次复测答案。

“点了完成”不是掌握证据。

### 场景 D：系统调整下一步

Trellis 根据证据提出以下三种结果之一：

- 继续：当前证据足够，进入下一项能力或更高难度；
- 补强：暴露了具体薄弱点，安排更小或不同支架的活动；
- 复习：即时表现尚可，但需要在延迟情境中再次验证。

低风险的活动粒度、提示和复习安排可以自动调整。跳过核心能力、改变目标、降低确认过的掌握等级或切换主路径，必须形成提案并由用户确认。

## 6. MVP 信息架构

MVP 不是四个平级功能页。它采用“一个学习工作台 + 按需展开的上下文”。

### 6.1 学习工作台（默认首页）

页面只回答四个问题：

1. 我现在在学什么？
2. 为什么下一步是这个？
3. 我现在具体要做什么？
4. 做完后怎样证明？

工作台组成：

- 当前阶段与能力焦点；
- 唯一主行动；
- 本周剩余核心活动，默认折叠；
- 最近证据与系统反馈；
- 路径变更提案，如有；
- 长期导师入口。

### 6.2 学习会话（任务空间）

从主行动进入，不作为顶层导航。根据活动类型使用不同模板：

- 解释型：唤醒已有知识 → 必要材料 → 主动解释 → 反馈；
- 判断型：给出情境 → 做出选择 → 说明依据 → 对照反馈；
- 实践型：明确产物 → 外部或内部完成 → 回收证据 → 复盘；
- 复测型：减少支架 → 新情境迁移 → 更新掌握假设。

用户始终可以自由提问，但聊天不能吞掉任务、证据和完成标准。

### 6.3 路径抽屉

路径是工作台的上下文，不是要求用户长期浏览的课程目录。按需展开时展示：

- 当前节点、前置和后续；
- 核心与条件性分支；
- 每个节点的学习状态和证据等级；
- 跳过、补齐和调整依据；
- 待确认的重大变更。

### 6.4 证据与评估

从当前能力或导师反馈进入。展示：

- 证据原文或链接；
- 证据对应的能力和量规；
- AI 判断、引用片段、置信度和未知项；
- 用户确认、纠正或要求复评；
- 下一次复测条件。

### 6.5 资源上下文

资源不作为独立“收藏网站”。资源只在目标、路径节点或活动上下文中出现，说明：

- 为什么推荐；
- 适用和不适用范围；
- 预计成本和时间；
- 权威等级与原始来源；
- 可替代项。

后台可以有完整资源库，MVP 前台不需要把它做成主导航。

## 7. 初次体验

首次流程分三步，而不是一张很长的考试表：

### 第一步：说明诉求

- 想解决什么问题；
- 为什么现在学；
- 希望最后能完成什么；
- 每周大致容量。

### 第二步：建立证据

- 自报基础只作为工作假设；
- 用户可以提供课程、作品和链接；
- 系统用少量高信息量情境任务检查关键能力；
- 可以分段完成和恢复。

### 第三步：审阅启动方案

系统用一页说明：目标解释、已知/未知、建议范围、第一阶段、首周活动和主要依据。用户确认的是“是否按这套假设启动”，不是逐条设计课程。

## 8. AI 导师

用户只感知一个长期导师，不展示诊断师、规划师、讲师、评审员等多个角色。

导师可以：

- 澄清目标；
- 解释下一步；
- 调整支架；
- 针对证据反馈；
- 提出路径修改；
- 帮助总结外部学习成果。

导师不可以：

- 仅凭聊天自报提升正式熟练等级；
- 静默跳过核心能力；
- 把推测写成用户事实；
- 用总分掩盖安全、隐私或高风险红线；
- 在没有来源和版本的情况下修改正式领域底图。

无模型密钥时，目标澄清、确定性评分、路径前置、任务说明和提案确认仍可运行。模型只增强开放回答反馈和自然语言解释。

## 9. AI 通识内容边界

首期内容包维持六项能力，但 PRD 不规定每一课的具体文案和题目。内容包团队负责：

- 从 UNESCO、NIST、官方模型文档、大学课程和高质量生产实践建立来源目录；
- 为每项能力设计可观察结果、前置、活动模板和量规；
- 把用户提供的两份历史课程表映射、去重、查漏，不直接复制为正式课程；
- 在发布前完成覆盖、偏科、版权和安全检查。

综合任务继续使用虚构咨询团队的“内部知识助手”作为首期候选情境，但必须在内容设计阶段验证它能覆盖六项能力。如果覆盖不完整，可以替换或增加情境，不把早期案例当作不可更改的产品定义。

## 10. MVP 功能范围

### 必须完成

- 学习诉求建立与恢复；
- 少量诊断和材料登记；
- 可解释的启动方案与用户确认；
- 一个默认学习工作台；
- 至少三种真实活动模板；
- 活动完成后的证据回收；
- 能力状态与熟练等级分离；
- 基于证据的继续、补强或复习决策；
- 一次路径调整提案与确认；
- 一次综合情境评估；
- 一次延迟复测；
- 无模型密钥回退；
- 刷新和重启后恢复状态。

### 暂不完成

- 多用户注册和团队管理；
- 公开课程市场；
- 多领域同时学习；
- 完整内置 AI 课程；
- 日历排程、打卡、连续天数和实时计时；
- 自动抓取并发布网络课程；
- 独立资源库首页；
- 多导师角色界面；
- 生产部署和 V0.1 数据迁移。

## 11. 成功标准

MVP 必须让一个真实学习者完成完整闭环，而不是只完成页面浏览：

1. 从学习诉求建立启动方案；
2. 完成至少三次不同类型的学习活动；
3. 留下至少两种不同形式的证据；
4. 完成一次综合情境任务；
5. 查看并确认或纠正一次量规评估；
6. 因证据发生至少一次可解释的路径调整；
7. 完成一次延迟复测；
8. 刷新、重启后状态和依据不丢失。

核心判断指标：学习者是否更清楚“为什么现在做这个”，系统是否真的根据证据改变了下一步，以及调整是否可以被理解和纠正。

## 12. 验收场景

### 新用户

输入目标后，不需要自己设计课程；能在合理追问后得到一份可理解、可确认的启动方案。

### 有材料用户

系统说明材料覆盖了什么、缺了什么；不会因用户填入课程名称就直接判定掌握。

### 自报与表现冲突

界面明确展示“自报基础”和“当前证据”不同；路径以表现证据为准，但可以调整解释和支架。

### 学习后表现不足

系统安排针对性补强，不只是把活动标红或重复同一内容。

### 重大路径变化

系统展示原因、影响和回退方式；用户未确认前，正式路径不变。

### 无模型密钥

整个闭环仍能运行，开放回答可以进入人工自检或规则化反馈，不出现空白页和阻断。

## 13. 待确认事项

本提案只需要确认以下产品级选择，不要求用户设计课程细节：

1. 是否同意“默认首页是唯一下一步的学习工作台”，而不是多个平级功能页。
2. 是否同意 MVP 必须走通综合任务、路径调整和延迟复测，不能在确认路径或第一次学习后停止。
3. 是否同意资源库退居上下文与后台治理，不作为 MVP 主导航。
4. 是否保留“内部知识助手”作为首期综合任务候选，而不是固定不可改的案例。
