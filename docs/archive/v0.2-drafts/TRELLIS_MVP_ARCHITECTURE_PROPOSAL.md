# Trellis MVP 产品与技术架构（提案）

> 状态：待确认  
> 日期：2026-08-13  
> 本文描述如何支撑 MVP 核心闭环，不代表已授权修改现有代码或数据库。

## 1. 架构目标

架构首先服务一个问题：系统如何依据真实证据，可靠地决定学习者的下一步。

它不以“有多少页面、多少表、多少 AI Agent”为复杂度指标。MVP 只建立以下能力：

```text
正式内容版本
    + 学习者目标和约束
    + 当前能力状态
    + 新产生的证据
            ↓
      下一步决策与解释
            ↓
     活动 / 复习 / 评估 / 提案
```

## 2. 架构原则

1. **下一步优先**：默认读取接口直接返回当前主行动及其依据，不要求前端拼装整个课程。
2. **证据优先**：完成记录、聊天自报和正式掌握是不同对象。
3. **内容与状态分离**：正式内容包是只读版本；用户运行状态独立保存。
4. **事实、推测、提案分离**：导师工作假设不能冒充用户事实；重大调整不能冒充正式路径。
5. **确定性内核**：前置检查、封闭题评分、状态迁移、幂等和权限由代码控制。
6. **AI 可替换**：AI 用于理解、反馈和解释，不拥有正式状态写权限。
7. **事件可追溯**：重要状态变化保留触发证据、规则版本和回退依据。
8. **渐进兼容**：V0.1 数据保持不动，新内核通过独立模型运行；迁移另做适配层。

## 3. 产品模块

### 3.1 学习工作台

职责：聚合当前焦点、唯一主行动、本周容量、最近证据、反馈和待确认提案。

它不是数据看板。前端只消费一个面向页面的 `LearningWorkspace` 读模型，避免分别请求路径、任务、资源、评估后自行推断下一步。

### 3.2 学习路径引擎

职责：

- 根据目标选择内容包范围；
- 检查能力前置；
- 合并自报、材料与表现证据；
- 生成初始路径和后续修订提案；
- 从候选活动中决定下一主行动；
- 在周容量变化时重新编排活动。

路径引擎输出的是有理由的决策，不是仅排序的一组课程标题。

### 3.3 活动与会话引擎

职责：把能力目标实例化为可执行活动，并维护学习会话连续上下文。

首期活动模板：

- `explain`：解释和主动提取；
- `scenario`：情境判断与依据；
- `practice`：完成小作品或外部实践；
- `review`：减少支架的延迟复测；
- `capstone`：跨能力综合任务。

活动模板定义流程、输入、证据要求和完成标准；具体 AI 通识内容由内容包提供。

### 3.4 证据与评估引擎

职责：

- 保存证据本体或安全链接；
- 将证据映射到能力和量规；
- 产生候选评估；
- 保存逐维度证据引用、置信度和未知项；
- 等待用户确认或纠正；
- 生成复测需求。

评估不是一个总分字段。每个能力判断必须能回到具体证据。

### 3.5 导师编排层

用户只看到一个导师。内部根据当前对象和意图选择诊断、讲解、反馈、规划或反思策略。

导师输出分为：

- 回答：不改变状态；
- 工作假设：带置信度，可被纠正；
- 低风险建议：可作用于支架和活动粒度；
- 正式提案：需要用户确认后才能改变目标或路径。

### 3.6 内容包与资源治理

职责：维护版本化领域结构，不参与用户运行时写入。

内容包包含：

- 领域和毕业结果；
- 能力节点与前置图；
- 可观察学习结果；
- 活动模板引用；
- 量规；
- 条件性分支；
- 资源映射；
- 来源、审核状态和变更记录。

用户的 Excel、链接和课程表先进入“用户材料”，经过映射后才能影响路径，不能直接变成正式内容包。

## 4. 前端信息架构

### 4.1 路由

```text
/                         → 学习工作台
/start                    → 首次诉求、证据建立和启动确认
/session/:activityId      → 当前学习会话
/evidence/:evidenceId     → 证据与评估详情
/proposal/:proposalId     → 重大调整确认
```

路径和资源不必在 MVP 中拥有顶层页面：

- 路径作为工作台抽屉或详情面板；
- 资源作为活动和能力的上下文面板；
- 导师作为全局连续入口；
- 设置只包含周容量、模型连接状态和隐私边界。

如果后续真实使用证明路径浏览或资源管理频繁，再升级为独立路由，不预先制造导航。

### 4.2 工作台读模型

```ts
type LearningWorkspace = {
  learnerGoal: GoalSummary;
  currentFocus: CapabilitySummary;
  primaryAction: ActionCard;
  weeklyPlan: {
    capacityMinutes: number;
    core: ActionCard[];
    optional: ActionCard[];
  };
  latestEvidence?: EvidenceSummary;
  latestFeedback?: FeedbackSummary;
  pendingProposal?: ProposalSummary;
  routeContext: RouteContextSummary;
};
```

`primaryAction` 必须包含：

- `whyNow`；
- `nextPhysicalAction`；
- `estimatedMinutes`；
- `expectedEvidence`；
- `completionCriteria`；
- `sourceRefs`；
- `possibleNextStates`。

## 5. 领域模型

### 5.1 内容层，只读且版本化

| 对象 | 作用 |
|---|---|
| `ContentPackVersion` | 一次可审计发布 |
| `Capability` | 可迁移的能力目标 |
| `CapabilityEdge` | 前置、支持或条件关系 |
| `ActivityTemplate` | 学习活动结构 |
| `Rubric` / `RubricDimension` | 可见掌握标准 |
| `Resource` | 权威材料或工具 |
| `ResourceMapping` | 资源与能力、活动的关系 |

### 5.2 学习者层

| 对象 | 作用 |
|---|---|
| `LearningIntent` | 用户目标、原因、深度与边界 |
| `LearnerConstraint` | 周容量、工具和现实限制 |
| `LearnerMaterial` | 用户已有材料及映射状态 |
| `LearnerCapabilityState` | 某能力的学习状态和当前熟练假设 |
| `MentorHypothesis` | 导师推测，非正式事实 |

### 5.3 路径与执行层

| 对象 | 作用 |
|---|---|
| `LearningRoute` | 用户确认的当前路径版本 |
| `RouteNode` | 能力在个性路径中的实例 |
| `RouteRevision` | 路径修订历史 |
| `WeeklyPlan` | 某周容量下的核心与可选活动 |
| `LearningActivity` | 可以执行的具体动作 |
| `LearningSession` | 一次连续学习上下文 |

### 5.4 证据与决策层

| 对象 | 作用 |
|---|---|
| `Evidence` | 回答、作品、链接或复测表现 |
| `Assessment` | 针对证据的候选判断 |
| `AssessmentDimension` | 逐能力/逐量规结论和引用 |
| `ReviewSchedule` | 延迟复测需求，不等于日历事件 |
| `ChangeProposal` | 需要确认的重大变化 |
| `DecisionEvent` | 正式状态变化的审计记录 |

## 6. 核心状态机

### 6.1 活动状态

```text
proposed → ready → in_progress → evidence_submitted
                                   ↓
                         reviewed / needs_revision
                                   ↓
                               completed
```

“完成按钮”最多把活动推进到 `evidence_submitted`；只有满足活动完成标准后才进入 `completed`。

### 6.2 能力学习状态

```text
unassessed
→ planned
→ learning
→ preliminary
→ validation_due
→ validated
↘ review_due
```

熟练等级 `0–3` 是独立字段。一次活动完成不能直接把学习状态改为 `validated`。

### 6.3 提案状态

```text
draft → pending → accepted
                ↘ rejected
                ↘ superseded
```

被拒绝的提案保留历史。重新计算产生新版本，不覆盖旧提案。

## 7. 下一步决策内核

下一步由候选活动评分产生，但必须满足硬约束。

### 7.1 硬约束

- 内容包版本有效；
- 前置能力状态满足要求；
- 活动未被完成或废弃；
- 周容量可容纳，或明确标记为跨周活动；
- 没有等待用户确认的冲突提案；
- 高风险活动具备人工确认点；
- 延迟复测在到期前不冒充当前核心活动。

### 7.2 排序信号

- 当前阶段关键性；
- 证据缺口；
- 前置解锁价值；
- 复习紧迫性；
- 用户目标相关性；
- 活动成本；
- 最近失败类型；
- 支架适配度。

### 7.3 决策输出

每次决策保存：

- 候选集合；
- 被选活动；
- 硬约束结果；
- 排序信号；
- 规则版本；
- 面向用户的简短解释；
- 可回退的上一状态。

## 8. API 边界

API 面向用例，而不是简单暴露每张表。

```text
GET    /api/workspace
POST   /api/intents
POST   /api/diagnostics/:id/answers
POST   /api/start-proposals/:id/confirm
POST   /api/activities/:id/start
POST   /api/activities/:id/evidence
POST   /api/assessments/:id/confirm
POST   /api/assessments/:id/correct
POST   /api/change-proposals/:id/confirm
POST   /api/change-proposals/:id/reject
GET    /api/sessions/:id
POST   /api/sessions/:id/turns
```

重要写接口要求：

- 带 `ownerId` 范围；
- 使用幂等键；
- 验证当前状态是否合法；
- 在事务中写业务对象和 `DecisionEvent`；
- AI 结构化输出先校验再进入候选记录；
- 返回新的工作台读模型或其版本号。

## 9. AI 服务架构

```text
页面/接口
   ↓
用例服务
   ├─ 确定性规则与状态机
   ├─ 内容包读取
   ├─ 证据存储
   └─ AI Gateway（可选）
          ├─ 开放回答反馈
          ├─ 材料映射候选
          ├─ 路径解释草稿
          └─ 导师自然语言
```

AI Gateway 必须：

- 使用版本化输入输出 Schema；
- 记录模型、提示版本、延迟和结果状态，但不记录密钥；
- 设置超时和结构校验；
- 低置信度、超时或无效结构时回退；
- 永远不直接执行正式路径修改。

无密钥回退：

- 封闭题由规则评分；
- 开放回答展示自检量规或进入待人工复核；
- 路径解释使用规则模板；
- 导师提供基于当前对象的预设追问和解释；
- 核心流程不因模型不可用而阻断。

## 10. 数据与隐私

- 所有用户运行对象必须有 `ownerId`。
- API 密钥只存在服务端环境变量，不进入数据库、日志、浏览器或 Git。
- 证据默认私有；外部作品优先存安全链接和摘要，而非复制全部原文。
- 不保存公司机密、政府标识、密码、Cookie、访问令牌和未脱敏简历。
- 评估保存证据片段引用，避免无法解释的孤立分数。
- 内容版本升级不覆盖历史路径和评估；旧版本继续可追溯。

## 11. 与 V0.1 的关系

V0.1 的 `records`、`weekly_reviews` 和四主线数据暂不迁移、删除或复用为新核心表。

MVP 采用旁路新内核：

```text
V0.1 兼容层 ──只读/独立维护──┐
                              ├─ Trellis 应用壳
V0.2 学习内核 ──新对象与 API─┘
```

后续迁移通过显式适配：

- V0.1 学习任务 → 候选 `LearningActivity`；
- V0.1 成果和证据 → 候选 `Evidence`；
- V0.1 路线阶段 → 路径背景，不直接等同于 `Capability`；
- 非学习项目继续留在兼容层。

## 12. 推荐代码边界

保留 Next/Vinext 现有根目录约束，但将新学习内核按职责组织：

```text
app/
  (learning)/                 # 工作台、首次启动、会话、证据、提案
  api/learning/               # 面向用例的接口
lib/learning/
  application/               # 用例服务
  domain/                    # 状态机、规则、领域类型
  content/                   # 内容包读取与校验
  ai/                        # 模型中立接口与回退
  persistence/               # 数据访问
db/
  schema/learning.ts         # V0.2 新表
content/
  ai-literacy/               # 版本化内容包，不与用户状态混放
tests/
  learning-domain/           # 规则与状态机
  learning-api/              # API 场景
  learning-e2e/              # 完整闭环
```

这不是要求立即大规模搬迁旧代码。编码时先建立边界，新文件进入正确位置；旧 V0.1 文件按后续迁移计划处理。

## 13. 实现顺序

### 切片 1：首次启动到真实下一步

- 学习诉求；
- 少量诊断；
- 启动方案；
- 用户确认；
- 工作台返回唯一主行动。

### 切片 2：活动到证据

- 三种活动模板；
- 会话连续性；
- 证据提交；
- 确定性完成标准和无模型回退。

### 切片 3：评估到调整

- 逐维量规；
- 用户确认/纠正；
- 继续、补强、复习决策；
- 路径调整提案。

### 切片 4：完整 MVP 周期

- 综合任务；
- 延迟复测；
- 完整审计历史；
- 端到端恢复与异常处理。

每个切片都必须从工作台开始并回到工作台，避免再次形成互不连贯的功能页。

## 14. 测试架构

### 领域规则

- 内容包无重复 ID、前置无环；
- 活动和能力状态迁移合法；
- 熟练等级不会因单次完成越级；
- 前置未满足时不能成为主行动；
- 重大变化必须产生待确认提案；
- 拒绝、重试和重复提交保持幂等。

### 用例与 API

- 首次启动、草稿恢复和启动确认；
- 自报与表现冲突；
- 无材料、有材料和材料偏科；
- 证据提交、评估确认与纠正；
- AI 超时、无效结构、低置信度和无密钥；
- 周容量变化后的重新编排；
- 路径调整的确认、拒绝和回退。

### 浏览器完整流程

- 新用户从目标进入主行动；
- 返回用户直接继续；
- 完成活动并看到证据反馈；
- 路径因证据发生可解释变化；
- 完成综合任务和延迟复测；
- 刷新和重新启动后状态恢复；
- 桌面和窄屏均保持唯一主行动清晰可见。

## 15. 架构验收门槛

开始重新编码前，必须确认：

1. 前台采用一个学习工作台，而不是多个平级后台对象页面。
2. 工作台主行动由服务端决策内核返回，不由前端临时拼接。
3. 活动完成、证据、评估和正式掌握是不同状态。
4. 内容包、用户状态和 AI 输出物理或逻辑分离。
5. 每次路径调整都可追溯、可拒绝、必要时可回退。
6. MVP 的完整闭环包含综合任务、一次调整和延迟复测。
7. 旧 V0.1 数据不被清空、覆盖或伪装成新学习状态。
