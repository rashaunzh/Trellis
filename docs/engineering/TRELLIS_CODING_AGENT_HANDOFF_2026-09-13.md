## 2. 对现有开发计划的评估

收缩方向合理：先证明材料判断与执行编排有用，避免把课程内容生产、自动批改和平台建设同时压入首轮。已有工程底座无需推翻。

但计划还需以下校正：

1. **“唯一根因”过于绝对。** 求解器把核心目标挤出去是已证实的重要机制；来源定位、时间可行性、反馈动作与恢复仍能独立导致用户无法使用。不能只修课程数量上限就结束重构。
2. **“已覆盖”只能声明安排了材料。** 必须继续核查材料实际读取范围、教学深度、前置与预算；不能把节点命中解释为学习结果有保障。
3. **四切片尚缺可追踪收口。** 每个未通过项应关联案例、页面操作、服务状态、缺陷和复测证据；不要重新写一份宏大 PRD。
4. **建议提高最终验收门。** 原 PRD 的维度 ≥1、无 0 分适合观察修复进展；若 1 表示“需修改”，则不能据此宣布可用。建议最终发布质量要求每项适用维度均“可用”，保留来源未知的明确限制。本建议不改写既有正式 PRD。
5. **旧审查中的市场差异化与壁垒是推断。** 目前没有足够用户研究证明需求规模、持续使用或竞争壁垒；本轮先验证具体使用价值，不写成已验证商业结论。

## 3. 交给 Coding Agent 的执行任务

按顺序执行，一次完成一个有证据的切片。下面的交互是交付合同，不要求所有用户经过完整诊断，不引入自制教学或生成式批改。

### T1：最新路线质量回归与修复（P0）

入口文件：`lib/learning/intelligence/curriculum-solver.ts`、`course-intelligence.ts`、`service.ts`、`route-review.ts`；复用 `scripts/acceptance/redesign/cases.mjs`、`model.mjs` 及现有五维量规。

- 先重跑旧失败案例作为回归，另冻结未参与修复的新保留案例；分别覆盖零材料、非编程起点、材料不符、低投入及目标过大。H1–H4 不再冒充未见案例。
- 对每条结果列出目标、核心内容、来源能证明的范围、前置、顺序、总投入与缺口。先写预期允许/禁止判断，再运行；不得只用节点覆盖断言代替产品评分。
- 不可行时，审阅首屏解释能做什么、不能做什么和原因；点击“补材料”回到保留背景的材料输入，点击“缩小目标”回到保留其他字段的目标编辑。修改后生成新草案，正式路线保持原样。
- 验收：没有目标核心悄悄消失、无依据的章节/背景事实或不可能的预算；所有失败与修复尝试保留。用固定样例调试，真实模型只用于有必要的质量复评。

### T2：路线审阅到章节实际开始（P0）

入口：`app/learn/page.tsx`、现有材料分析与位置补充服务、`route-review.ts`；先读取相关组件与测试再修改。

- 输入目标和材料后，先看到材料读取状态、采用理由与限制，再看到阶段目标、当前周承诺及第一行动；其他材料按原因折叠，不默认展开长清单。
- 点击“开始”打开已验证的具体位置；只有课程主页时明确标为主页并给可依据来源提供的查找路径。无法知道章节时不编造路径，提供补充位置或替换材料入口。
- 外部课程返回后保持任务、输入和位置；确认路线成功后直接承接首任务，不要求再次确认同一决定。
- 桌面 1440px、手机 390px、键盘各走查一遍。录下每一步点击、出现内容、保存对象及失败承接。
- 验收：真实访问抽样能到达所声称的位置；5 名首次使用者中至少 4 名在快速规划场景 10 分钟内开始首活动。招募未完成时标待验收，不让 agent 模拟真人计数。

### T3：反馈产生明确动作与阶段出口（P0）

入口：`app/learn/page.tsx`、`lib/learning/intelligence/feedback-draft.ts`、`service.ts`、`decision-kernel.ts`。

- 复用已完成分流；不要重新实现第二套反馈表单或信号模型。
- 完成未验证 → 保存完成事实并显示“未独立验证”；测验自报 → 记录出处与用户报告，不当作平台判分；具体卡点 → 显示针对本任务的帮助或补学建议；时间不足 → 保存约束并预览安排影响。
- 阶段结束显示本阶段目标、已有证据和仍待验证内容；读完课程不能自动声称能力掌握。证据不足时允许结束本轮学习记录，但不得伪造阶段能力通过。
- 所有改变已确认计划的建议进入差异预览；说明替换什么、原因、投入影响，确认才生效。拒绝后记录仍保留，正式计划不变。
- 验收：四分支分别提交、刷新、回读；反馈引用实际本次输入；无通用套话冒充有效补救；不同阶段出口不可只替换名称。

### T4：确认与恢复的完整性收口（P0）

入口：已有调整/确认 API、`service.ts`、`scripts/acceptance/redesign/browser.mjs` 与领域回归测试。

- 建立“入口 → 修改对象 → 确认点”表，覆盖受阻反馈、周调整、材料变更、路线修订，寻找绕过提案的正式写入。
- 浏览器执行：调整预览 → 拒绝 → 刷新原计划 → 新提案 → 确认 → 刷新新计划。查看反馈不是确认调整。
- 注入重复点击、成功响应丢失、多标签旧提交、取消后迟到响应、生成期间刷新、服务重启和跨用户请求。API 只准备/核对数据，不能替代主链操作。
- 验收：输入可恢复；一次业务写入；旧状态不覆盖新状态；跨用户不可读写；反馈保存与评价/建议失败能够分别重试。

### T5：工作台入口兑现与最低可观测性（P1，阻塞入口升 P0）

入口：`app/workbench/page.tsx`、`app/grow/page.tsx`、现有日志与模型耗时记录。

- 逐个点击工作台材料、检查、成果入口，记录真实服务承接。投影数量不可标为已执行检查；没有实现的能力清楚标注限制，冻结功能不放在主要行动路径。不要借此扩建自动批改平台。
- 学习页与工作台读同一个任务、材料和证据对象；回访直接显示上次任务/反馈及继续入口。
- 利用现有日志报告保存失败、模型等待、重试及可恢复情况；不新建分析表。保存成功以服务端结果为准，不以点击计数。
- 小样本报告原始次数、最大等待和失败原因；数据缺失为未知，自动化与真人分开。不采集私有答案或完整提示词到分析事件。

### T6：真实使用后的修改复测（放行门）

- 先用线上所有者身份走完整保存、退出重进及恢复；托管平台发布成功不能代替此检查。
- 所有者完成三次真实任务、至少两种活动/反馈情境和一次隔日恢复；首次使用者走查按现有目标招募，不能用 agent 自演。
- 每次记录任务、卡住的具体一步、耗时和用户原话；整理缺陷 → 修复 → 同任务复测。至少完成一次此闭环。
- 只对本轮课程编排范围作可用声明；不宣称八周学习效果、不声明生成式批改已验收。

## 4. 统一验收与节省额度

每个切片交付：代码差异、受影响业务测试、实际点击链与截图、数据读回结果、未通过项、下一步。不要只交设计文档。

常用命令：

```powershell
npm run test:domain
npm run acceptance:redesign-core -- --phase=judgment
npm run acceptance:redesign-core -- --phase=browser
# 内容/模型判断有必要复评且环境可用时才执行，不在每次 UI 修改后反复调用
npm run acceptance:redesign-core -- --phase=model
# 切片收口运行一次完整工程门；不是每次微小编辑后运行
npm run check
```

验收脚本会因缺少人工证据输出待验收；读取 `result.json` 区分自动检查失败和发布门未通过。不得把退出状态改绿来隐藏缺口。无模型时验证诚实降级，不能计为真实模型质量通过。

Coding agent 负责代码、固定样例、浏览器和缺陷修复。高成本模型仅在 T1 路线语义复评及最终产品审阅使用；输入本文件、收缩 PRD、最新差异和失败证据，避免反复装载整段历史。已通过的测试无新增风险时不重复运行。保持一个分支顺序合入，避免不同 agent 同时改核心服务与学习页。

建议给 agent 的启动指令：

> 读取 AGENTS.md、最新 handoff、收缩版 PRD 和本交接。以 T1 开始，先确认哪些行为在当前代码已完成，仅修复有证据的缺口；每个切片完成实现和验收后继续下一项。不新增课程平台、模型工作流、数据表或平行运行时，不重写已完成反馈分流。保持正式计划确认门与兼容记录。每次提交报告用户可见改变、证据与尚未放行条件。真人参与不足时完成可独立推进的工程工作，并明确留出真人验收。

## 5. 计划边界与依赖

T1–T4 是核心链收口，T5 防止周边入口继续制造虚假能力预期，T6 决定能否称为真实可用。尚无足够缺陷复评数据承诺总工期；T1 完成后按剩余缺陷逐项估算，不用页面数量估进度。

长期学习效果、课程内容包、雅思、生成式成果批改、作品陈列室扩展均留在候选区。历史完整交付文档继续作为需求来源保留，不作为当前 agent 的并行待办。
